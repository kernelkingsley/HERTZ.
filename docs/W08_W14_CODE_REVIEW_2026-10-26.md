# W08-W14 independent review — 26 October 2026

## Verdict

W08-W14 remain **In progress**. Their API contract tests pass, but the regressions explicitly leave their defining Unity, runtime, device, integration, or deployment acceptance paths pending. A green `regress:w08-w14` is regression health, not milestone completion.

## Blocking findings

### W08 — material/lighting proof and undo are incomplete

- No fresh live Unity proof demonstrates two independent Poly Haven surfaces on a floor and wall, persistence after reopen, real TerrainLayer application, or HDRI environment application.
- `HertzStudioMaterialCommands.Undo` ignores `expectedUnityRevision`, performs the global last Unity undo rather than an operation-scoped undo, does not save the reverted scene, and does not advance/return a trustworthy content revision.
- HDRI changes mutate `RenderSettings` and a shared generated sky material without a complete operation-scoped undo/rollback proof.
- The regression proves request validation and offline failure only; it cannot satisfy W08 acceptance.

### W09 — animation assignment is not connected to runtime definitions

- `AnimationAssign` creates/updates a generated controller but does not bind it to `HertzCharacterDefinition` or `HertzEnemyBehaviorProfile`.
- A new AnimatorController may have no default state; the code only replaces motion when `defaultState != null`, so it can report success without assigning a playable clip.
- Posted loop, speed, transition, and root-motion settings are stored by the API but are not applied by the Unity command.
- Rig validation checks that the clip asset has a valid Humanoid avatar, but does not prove source/target avatar compatibility or retargeted playback.
- There is no Unity Play Mode proof for enemy wait/rush/attack transitions or visible player-body animation while tracked XR transforms remain untouched.

### W10 — Editor performance capture is fabricated from static inspection

- `PerformanceEditorCapture` wraps static scene counts, hardcodes 60 Hz, five seconds, and one sample, and does not measure Editor CPU/GPU frame time, FPS, batches/draw calls, or samples over time.
- Static inspection does not currently trace findings back to concrete asset/object identifiers as required.
- A real local capture has not been verified. Quest remains correctly pending.

### W11 — restore is a placeholder and capture selection is truncated

- `SnapshotsRestore` writes nothing and returns `status:"staging"` with a random safety snapshot ID; there is no staged atomic restore, pre-restore snapshot, hash revalidation at apply time, rollback, or reference verification.
- Snapshot capture silently stops after roughly 80 discovered paths, so it can create an incomplete manifest while appearing successful.
- No end-to-end proof edits surface/model/profile state, reopens, diffs, restores, preserves GUIDs, rejects corruption, and recovers from a failed restore without losing unrelated later changes.

### W12 — no encounter runtime exists

- Apply persists request JSON but does not create a typed/versioned Unity encounter asset or bind a runtime scheduler.
- Runtime play/pause/reset returns an acknowledgement without spawning, timing, cancellation, deduplication, or reset behavior.
- Validation loosely searches JSON text instead of authoritatively resolving profiles, prefabs, spawn points, triggers, and protected XR targets in Unity.
- There is no isolated Play Mode proof that moving a spawn point or delay changes execution, reload persists it, and reset avoids duplicates.

### W13 — aggregate incorrectly treats partial contract suites as integration proof

- `regress:w13` considers W08-W12/W14 successful when their API tests exit zero, even though each proof lists its decisive vertical acceptance path as pending.
- Keyword matching (`unity|vertical|fail|offline|provenance|authoritative`) is not evidence that modules work together.
- W13 lacks a real cross-module workflow, delayed Unity reconnect/apply-once proof, restart/lost-ack/conflict/auth/quota recovery, production latency/loading measurements, player-assembly exclusion verification, and hosted/second-device evidence.

### W14 — planning surface only

- The current implementation intentionally stops at `preview_only`; no provider adapter, read-only account/credit validation, artifact publication, DNS binding, HTTPS/auth/API/storage/connector verification, or rollback execution exists.
- This is honest and should remain In progress until Kingsley selects a provider and supplies the required credential references. It must never claim success from a preview or fake response.
